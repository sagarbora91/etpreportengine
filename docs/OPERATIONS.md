## Accounts, files and trust

Use separate Windows identities for the Owner, shared staff login, and unattended automation. The automation account must be an enabled local account, outside Administrators, and must not be SYSTEM, Local Service, Network Service, or the built-in Administrator. Give it an active `STORE_MANAGER` application entry and the `etp_store_manager` database role. It is separate from the shared interactive staff login.

Install the application and scripts beneath an administrator-controlled directory, normally `C:\Program Files\Saagar Traders\ETP Reporting Engine`. Task setup rejects writable installation files, unsafe ancestor permissions, links and junctions, a folder holding a checked program (the application or Sqlcmd) in which anyone but administrators may create files, and paths on network shares, mapped drives or SUBST drives. Install Microsoft Sqlcmd in a protected Program Files location. Do not make the installation writable to solve a permissions failure.

`%ProgramData%\EtpReporting\Operations\operations.json` is the common machine target for unattended imports, backups, drills and configured setup. It contains the local SQL instance, database and dedicated automation identity, without a SQL password. Only administrators may change it; the automation identity reads it. Interactive saved connection settings are separate: verify that Owner and staff point to this same database. `--initialize-database` uses interactive saved settings; `--initialize-configured-database` uses the protected machine target.

Connections use Windows authentication. The default local setting is `Encrypt=Optional`; remote hosts, TCP endpoints, explicit `Encrypt=False`, attached database files and SQL credentials are rejected. Bootstrap supports ordinary local default or named instances; LocalDB and custom named-pipe endpoints require a separately reviewed manual setup.

### Folder policy decision

`initialize-etp-operation-folders.ps1` resets existing permissions, including explicit permissions on descendants. Schedule this with the shop closed and verify the chosen SQL service identity first.

By default, `Backups`, `Documents`, `Share`, `SetupLogs` and the automatic-import folders `Inbound`, `Processed` (with `Processed\Duplicate`), `Failed` and `ReportPacks` beneath `%ProgramData%\EtpReporting` allow SYSTEM and Administrators full control, and the SQL service and dedicated local `EtpAutomation` account Modify. The parent `EtpReporting` folder and `Operations` give the SQL service and automation account read access. The parent is protected too, so a broad parent grant cannot be used to replace a protected child. Inheritance from broad Windows groups is removed.

### SQL operations module

`install-etp-sql-operations.ps1` installs a database-specific `etp_operations_<hash>` procedure in `master`, with the database and backup/restore roots fixed at installation. Calls accept only the supported operation and a constrained backup filename. The procedure verifies the caller's active application role. Backups and metadata checks are open to the dedicated account. The drill is refused to anyone but a SQL administrator; it creates an isolated `EtpRecovery_<guid>` database and refuses the backup if the restored copy has TRUSTWORTHY or cross-database ownership chaining on.

Row counts (A4.4, 1.9.3). The broker counts `sales_invoices`, `sales_lines`, `import_files` and `daily_reporting_days` with `COUNT_BIG(*)` immediately before and immediately after `BACKUP`, and returns both as an `ETP_ROWCOUNTS:` line after the backup metadata. The drill counts the same four tables in the restored copy, after `DBCC CHECKDB` and before the copy is dropped; nothing outside the procedure can see the copy, so it has to be counted there. A count that fails is returned as missing; it never fails a backup. No extra locks are taken (`BACKUP` cannot run inside a transaction, and holding the automation lease would skip a cycle and still miss manual imports): an import that writes while the backup runs makes the two counts differ, and the receipt then records no counts and says so.

Each module has its own signer, `EtpOperationsModuleSigner_<hash>`: a certificate and login that give that one procedure `CREATE ANY DATABASE` and `VIEW SERVER STATE`, which reading a backup's contents and refusing to overwrite a file require. No database master key is involved. The certificate is protected by a password generated inside SQL Server and never recorded, and its private key is removed as soon as the procedure is signed. The signature still verifies, but nothing can be signed with that certificate again; reinstalling creates a new one. It is not the backup-encryption certificate and is not the Windows task login. Earlier builds used one shared `EtpOperationsModuleSigner` with a live private key and `ALTER ANY DATABASE`; the installer removes it once nothing is signed with it. Altering the module requires a reinstall. Do not give the automation account `sysadmin` or `dbcreator` to resolve a failed drill: the drill is the Owner's.

After the drill, its result is recorded as the dedicated account's database user. The recording procedures live in the application database, where any application Owner can change them, so they never run with the drill's administrator rights. The recording is refused if the database is marked TRUSTWORTHY.

The installer grants the dedicated account module execution, backup-certificate visibility where the edition encrypts, `db_backupoperator` on the application database, and `etp_automation` for verified status recording. Reprovisioning an application account removes its automation and backup-operator memberships. After an approved account change, review and reapply the dedicated setup explicitly. The master module also checks active application role at each call; remove its old direct grant when retiring an automation identity.

## Certificate and password custody

In Owner **Settings → Database → Encrypted backup recovery keys**, choose two connected, separate recovery folders, confirm that both provide an off-PC copy, and enter a password of 16–128 characters. Select **Create and export recovery keys**.

SQL Server writes a uniquely named `.cer` and password-encrypted `.pvk` into each folder. Its service identity needs write access; the Owner process must be able to read the exports and write `%ProgramData%\EtpReporting\Backups\certificate-custody.json`. Strict folder permissions may require a supervised elevated setup session. Regular Owner day reopening does not require Windows elevation.

Each export creates a unique, never-overwritten `certificate-custody-<thumbprint>-<exportId>.json` receipt containing the certificate thumbprint and both file hashes, without the password. `certificate-custody.json` is only the latest pointer used when creating new backups; each backup receipt retains its exact immutable custody receipt and matching thumbprint. Re-exporting the same certificate or rotating to a new certificate cannot redirect older backups to different recovery copies. Preserve every custody receipt needed by retained backups. Directory checks reject duplicate/nested locations and links, but cannot prove physical independence or successful cloud synchronisation. Sagar must verify that the copies exist away from the PC and remain retrievable. Store the export password separately, with a documented recovery custodian. If the service creates a new `master` database master key, the supplied password also protects that key; retain it accordingly.

Preserve the original certificate/private key for as long as any retained backup needs them. Do not overwrite an old recovery export or replace the encryption certificate without preserving its recovery material. Microsoft documents that the original matching certificate is required for restoring encrypted backups. [Encrypted backup recovery requirements](https://learn.microsoft.com/en-us/sql/relational-databases/backup-restore/backup-encryption?view=sql-server-ver17).

Daily backup validates recorded custody and the current SQL certificate thumbprint. It can run while recovery media are disconnected. A recovery drill requires both recorded copies to be accessible and match their hashes; reconnect them at their recorded locations before the drill. Copying only the custody JSON is insufficient. Retain a separate off-PC copy of the encrypted database backup and its receipt for machine-loss recovery; automatic off-PC backup replication is not implemented by these scripts.

## Backup, retention and task behaviour

| Task | Default schedule, local time |
| --- | --- |
| ETP Reporting Daily Backup | Daily at 22:00; configurable `-RunTime`. |
| ETP Reporting Monthly Recovery Drill | Daily runner at 08:00; performs the drill only on day 1 by default. `-DayOfMonth` accepts 1–28. |
| ETP Reporting Automated Operations | Every five minutes by default; imports approved sources and generates scheduled packs. |

Daily Backup and Automated Operations run as the dedicated account at Limited run level. The recovery drill runs as the Owner at Highest run level: a UAC-filtered token loses `BUILTIN\Administrators`, so an Owner who is a SQL administrator only through that group would lose it inside the task. All use S4U logon, StartWhenAvailable, IgnoreNew for overlap, and a two-hour execution limit. The monthly runner's day check means a missed run caught up on another day does not perform the missed drill; run a manual drill and inspect its evidence. Task scheduling does not prove that a job succeeded.

A backup uses a unique filename and SQL `COPY_ONLY`, `CHECKSUM`, `RESTORE VERIFYONLY`, and AES-256 encryption on an edition that supports it. On Express and Web the encryption clause is omitted and the receipt records `NONE`. After SQL verification, the script writes `<backup>.receipt.json` and `<database>-latest-verified.json`, containing the exact path, length, SHA-256, certificate reference and backup file metadata. These files contain paths and belong in the protected backup folder, not a general support attachment.

Rotation keeps the newest valid backup for each of the latest 14 UTC days represented in the receipts, plus the newest for each of the latest 12 UTC months represented. Overlapping selections count once; this is not necessarily 26 files. Only verified receipt/file pairs for the configured database are eligible for deletion. Unknown or invalid files remain for administrator review. These are copy-only full backups; the scripts do not provide transaction-log backup or point-in-time recovery scheduling.

**Rotation never deletes a safety backup.** A receipt records its `purpose`: `SCHEDULED` for the nightly backup, `PRE_MIGRATION` for the copy setup takes before it applies migrations, and `PRE_ROLLBACK` for the one taken before a release rollback. Only `SCHEDULED` backups are ever removed, and a safety backup does not occupy a daily or monthly slot, so taking one never shortens the ordinary history. A receipt from an older build has no `purpose` and counts as scheduled; a `purpose` this build cannot read is kept rather than deleted. Before 25 September 2026 none of this existed: on the owner's PC, setup's 08:50 pre-migration backup was deleted by the rotation that ran with the next backup an hour and a half later, which is why the deployment sequence still asks for an independent backup into the SQL backup folder before an upgrade. **Safety backups therefore accumulate** — one per *attempt*, not one per upgrade: a setup run that fails after taking its pre-migration backup leaves that copy behind, and the next attempt takes another. Each is the size of the database. Delete one by hand, with its `.receipt.json`, once the upgrade it protected has been proven in use. Whether the product should cap them automatically is an owner decision, not a default this code should pick.

Rotation normally runs at the end of a successful backup. If the drive is below the free-space limit, the backup now reclaims expired scheduled backups **before** refusing, and refuses only if that was not enough — saying how much it recovered. Without that, a folder that had grown past the limit could never shrink by itself: the backup refused before it started, rotation never ran, and every night repeated it until somebody deleted files by hand. Nothing the retention policy keeps, and no safety backup, is touched on that path.

The drill selects the file named by the latest verified receipt, validates its hash and custody copies, compares its metadata, restores every supported data/log file into an isolated database, runs `DBCC CHECKDB`, compares restored file metadata with the backup, and removes the isolated database. The hash is checked again before success. It never compares today's live row counts with the backup: imports since the backup cannot cause a false failure. A successful drill proves restoration and these integrity/file checks; it does not reconcile business-report totals.

**Row counts (A4.4, 1.9.3).** The receipt records `rowCounts`: the four counts the broker took, when the counts before and after `BACKUP` were equal. Otherwise it records `rowCountsNotRecorded` and the reason: `CHANGED_DURING_BACKUP` (an import wrote while the backup ran), `OPERATIONS_MODULE_OUTDATED` (the backup was taken through a broker from before 1.9.3) or `COUNT_FAILED`. A receipt from before 1.9.3 has neither. The drill compares the receipt's counts with its count of the restored copy:

- All four equal: the drill passes.
- Any table differs: the drill **fails**, and the message names each differing table with both numbers (`sales_lines: receipt 5401, restored copy 5400`). It writes `<database>-latest-drill.json` with `succeeded: false`, records the failure (see below) and an `operational_audit` row `RestoreDrill` / `Failed`, and records no verified drill.
- The receipt has counts but the broker returned none: the operations module is from before 1.9.3, and the drill fails and says to reinstall it (run setup again, or step 7). If the restored copy could not be counted, the drill fails and says so.
- The receipt has no counts: the drill passes, and says so in its output, in `latest-drill.json` (`rowCountsNotRecorded` and `rowCountsNote`), in its audit row ("row counts were not recorded by this backup") and on System status. It is never shown as an ordinary pass. The next backup taken with 1.9.3 records counts.
- A receipt whose counts are malformed, or that carries both fields or a reason this build did not write, fails the drill.

**A4.4a: proving that the drill catches a wrong count.** `invoke-etp-recovery-drill.ps1 -ReceiptPath <file>` drills the backup another receipt names instead of `<database>-latest-verified.json`. The file must be a `.json` directly in the backup folder and is verified exactly like the latest receipt (backup path, size, SHA-256, custody). As administrator: copy `<database>-latest-verified.json` to a new name in the backup folder that does not end in `.bak.receipt.json` (for example `rowcount-check-copy.json`, so rotation never reads it), change `rowCounts.sales_lines` by one, and run the drill elevated with `-ReceiptPath` naming the copy. It must fail naming `sales_lines` and both numbers, `operational_audit` gets a `RestoreDrill` / `Failed` row, and System status shows the failure. Then run the drill again without `-ReceiptPath`: the original receipt passes and System status returns to passed. Delete the copy afterwards.

Every drill that reaches the comparison writes `<database>-latest-drill.json`: `succeeded`, the backup hash, the time, and `rowCounts` as four `{table, receipt, restored}` pairs, or `rowCountsNotRecorded` with `rowCountsNote`. That file is in the protected backup folder, which the application, running unelevated, cannot read. So the drill also records its result in `dbo.recovery_drill_results` (migration 0045, append-only, written only through `dbo.record_recovery_drill_result` by the operations account or an Owner, like the verified-operation record), and System status and the dashboard read the latest row through `dbo.load_latest_recovery_drill_result`: "Latest recovery drill result" shows Passed or Failed with the four pairs (one line per table, Matched or Differs), or the reason there were none. A failed latest drill is a critical warning (`RECOVERY_DRILL_FAILED`) until a drill passes. The audit row cannot carry the numbers: audit details may not contain digits. A passed drill also writes the protected SQL status record. System status shows separate UTC times and fingerprints for the latest backup and latest successful drill; a newer backup can correctly have a different hash from the drill. Backup absence is critical; backup age over 36 hours, missing drill, or drill age over 45 days produces a warning. Generic audit events cannot publish trusted recovery health. Staff read safe status through a database procedure without `msdb` access.

## Second-machine recovery exercise

**Required deployment evidence; not yet verified here.** Use an isolated second machine and a reviewed compatible SQL version. Keep the live shop database untouched. Retain the original backup, its receipt, both custody copies and the separately held password.

1. Verify the backup SHA-256 and length against its receipt. Verify each `.cer`/`.pvk` hash against the custody receipt. Work from copies in a protected recovery directory; give the recovery SQL service only the necessary file access.
2. As SQL administrator on the second machine, create a database master key in `master` if one is absent, then import the matching certificate and private key. Use a private administrative session and substitute the actual recovery files/passwords; do not save passwords in shared scripts or logs. For example:

   ```sql
   USE master;
   -- Create only if this instance has no database master key.
   CREATE MASTER KEY ENCRYPTION BY PASSWORD = '<new recovery-instance master-key password>';
   CREATE CERTIFICATE EtpBackupCert
     FROM FILE = N'<protected recovery directory>\EtpBackupCert.cer'
     WITH PRIVATE KEY
     (FILE = N'<protected recovery directory>\EtpBackupCert.pvk',
      DECRYPTION BY PASSWORD = '<original export password>');
   ```

   Do not replace an existing certificate with a different thumbprint. Confirm the imported thumbprint matches the receipt. The import sequence follows Microsoft's [encrypted backup recovery documentation](https://learn.microsoft.com/en-us/sql/relational-databases/backup-restore/backup-encryption?view=sql-server-ver17).
3. Run `RESTORE VERIFYONLY ... WITH CHECKSUM` and `RESTORE FILELISTONLY` for the verified backup. Restore to a new, unused database name, with `MOVE` entries for **every** listed data/log file into the isolated recovery directory. Do not use `WITH REPLACE` or the live database name. The installed drill script is not a second-machine restore tool: its configuration and receipts refer to the original machine's paths. Nor is `restore-etp-database.ps1`, which makes a backup the live database on a new PC (below) and is not for test restores.
4. Set the restored database's `TRUSTWORTHY` and `DB_CHAINING` options OFF. Run `DBCC CHECKDB`. Compare restored file IDs/logical names with the backup metadata; inspect the migration journal and representative report/import records at the backup's date.
5. Record the SQL version, certificate thumbprint, backup hash, restored database name, checks and outcome in restricted recovery evidence. Demonstrate recovery from the second custody copy too, using a clean isolated instance so an already-imported key cannot mask a missing/wrong copy. Remove only the explicitly identified test database and temporary recovery copies when the exercise is approved; retain the original recovery material.

### Moving the live database to a new PC

When a new PC replaces the old one and carries on with its data (steps also in `docs/INSTALL.md`):

1. Run setup elevated with **Create a new empty ETP database** unticked. With no database present, setup prepares SQL Server, the protected configuration and the master operations broker (`install-etp-sql-operations.ps1 -BrokerOnly`, which creates it only if it is missing, replaces it only if it is unsigned and from an earlier build, and never alters a signed one), creates no database and no tasks, and ends with exit code 0 and `DATABASE-RESTORE-PENDING.txt`. An existing database is upgraded as usual whatever the option says.
2. Run `restore-etp-database.ps1 -BackupPath <.bak> [-ReceiptPath <.bak.receipt.json>]` elevated, as a SQL administrator. It takes the instance and database from the protected configuration and refuses, changing nothing: a network path, a file inside `%ProgramData%\EtpReporting`, a receipt whose SHA-256 or size differs, an encrypted backup, and any database that already exists — it never restores over one. It copies the backup into a protected folder only SQL Server's service can read and checks the copy's hash; checks with `RESTORE HEADERONLY` (one full backup of the configured database), `RESTORE VERIFYONLY … WITH CHECKSUM` and `RESTORE FILELISTONLY` (one data and one log file); restores with `MOVE` into the instance's default data and log folders; sets `TRUSTWORTHY` and `DB_CHAINING` off; and runs `DBCC CHECKDB`. It then performs the Owner recovery below for the Windows account running it, with a recorded reason, gives that account `ALTER ANY LOGIN WITH GRANT OPTION` through the same one-off SYSTEM task setup uses ([Owners and SQL Server logins](#owners-and-sql-server-logins)), and installs the broker if it is missing. Its log is `%ProgramData%\EtpReporting\SetupLogs\restore-*.log`. **Restore only an ETP backup from a trusted source:** the Owner recovery and setup's migrations run the database's own procedures and triggers as a SQL administrator. The helper refuses, before either runs, a database-level DDL trigger or any trigger on `dbo.application_users` other than `trg_application_users_history`, which ETP never creates; it cannot detect a changed body of ETP's own code.
3. Run setup again. It installs the broker if it is still missing (`-BrokerOnly`, as for any existing database with waiting migrations), takes and verifies the pre-migration backup through it, then applies the waiting migrations (0033–0037 for a 1.8.x database) and installs the tasks.
4. Start ETP (no Run as administrator needed; see [Owners and SQL Server logins](#owners-and-sql-server-logins)) and, as Owner, add `<PC>\EtpAutomation` as an active Store Manager in Settings → Users.
5. Run setup once more. It installs the operations module for that account (deployment step 7), which the daily backup and the monthly drill need; the setup log says so, or says what is still missing.

Restoring onto a newer SQL Server upgrades the database for good: nothing backed up afterwards restores onto the older version. The old PC's accounts stay listed in Settings → Users and cannot sign in. Deactivate them there (untick Active, give a reason): since migration 0042 (1.9.3) `dbo.configure_application_role` no longer tries to create a SQL login when deactivating, so an account of a PC that no longer exists can be deactivated; its database roles are dropped, `CONNECT` is denied and the change is in the user history as usual. Such an account can never be given access again (Windows cannot find it), and the last active Owner can never be deactivated or demoted. Before 0042 this needed a SQL administrator's script. Migrations 0033 and 0037 refuse duplicate non-rejected accounting batches (Phase 5 upgrade checks below); the helper warns when it finds them, and when the server's collation differs from the database's, which the monthly drill cannot handle.

## Owner recovery and maintenance

Retain an approved SQL administrator recovery path separate from the shared staff account. Windows administrator membership alone does not guarantee SQL administrator access.

For a locked business date, the normal Owner uses the app's reopen action with a reason. SQL validates `etp_owner` membership and records the reason and SQL actor atomically. A client administrator flag, direct row deletion, or moving the date is not a recovery method.

If all working Owner access is lost, stop unattended activity and have the approved SQL administrator connect locally to the correct database. Verify the intended Windows identity, then in one reviewed transaction call `dbo.configure_application_role` with that identity, `OWNER`, and active status, and create/update its matching `dbo.application_users` row with a non-empty recovery reason, `modified_by=SUSER_SNAME()` and current UTC time. Both SQL membership and the application entry are required. Preserve the user-history/audit records and last-Owner guard. Sign in as the recovered Owner, verify access, and remove any temporary access. Do not promote the shared staff account, disable audit triggers, or rewrite migration checksums to regain access.

### Owners and SQL Server logins

Since 1.9.3 (migration 0043, Sagar's decision of 2 October 2026) every active Owner's SQL Server login holds **`ALTER ANY LOGIN WITH GRANT OPTION`**. Every change in Settings → Users ends with a server-level `GRANT` or `REVOKE` of `ALTER ANY LOGIN`, which SQL Server allows only to `sysadmin`, `CONTROL SERVER` or a holder of the grant option. Since 1.9.2 the Owner is `sysadmin` only through `BUILTIN\Administrators`, which Windows removes from an unelevated token, so before 0043 an Owner who opened ETP normally got SQL error 4613 on every save and had to use **Run as administrator**.

**This is the Owner's sanctioned power, and it is a server-level one.** Without elevation, an Owner can:

- create a SQL Server login for **any** Windows account, local or domain, and give it ETP access as Store Manager, Viewer or Owner;
- make another account an Owner, which passes the same right on (that is what the grant option is for);
- through `ALTER ANY LOGIN` itself, disable, rename or drop other logins on the instance that are not SQL administrators (audit finding 1.10, `docs/audit/claude-audit-2026-09/04-security.md`).

It does not make the Owner a SQL administrator: an Owner still cannot restore databases, run the recovery drill or change `sysadmin` logins. Treat every Owner's Windows account as a privileged account, and give the Owner role only to people trusted with the instance's logins. Store Managers and Viewers never hold the grant option; `dbo.configure_application_role` revokes `ALTER ANY LOGIN` from anyone it makes a non-Owner.

How changes behave:

- **Adding or promoting an Owner** grants `ALTER ANY LOGIN WITH GRANT OPTION`. The granting Owner is recorded as the grantor.
- **Demoting or deactivating an Owner** revokes it `WITH CASCADE`, which also takes it back from every account that Owner granted it to. In the same change every remaining active Owner with a login that lacks it is given it again, so an Owner made by the demoted one keeps it. Three cases are refused, with nothing changed: taking away **your own** Owner access while you hold the right (51472, ask another Owner); a revoke that SQL Server did not complete because somebody else granted the right (51473, run ETP as administrator and save again); and a demotion that would remove **your own** right because the account being demoted gave it to you (51474, a SQL administrator must make the change).
- Settings → Users, setup and the restore helper always run the procedure in a transaction. A SQL administrator calling it by hand must do the same, or a refused change can be left half-done.

**The account that ran setup or the restore helper.** SQL Server never lets a login grant a permission to itself (error 4627, a warning; the statement is skipped). Setup and `restore-etp-database.ps1` run as the person who becomes the Owner, and migration 0043, which grants the right to every other active Owner on an existing install, skips the account running it. So since Sagar's decision of 2 October 2026 a **different** SQL administrator gives it: setup, and the restore helper after its Owner recovery, check whether an active Owner lacks it and, if one does, have `NT AUTHORITY\SYSTEM` grant it through a one-off scheduled task (`Invoke-EtpOwnerGrantOptionAsSystem` in `scripts\etp-operations-common.ps1`). On an instance ETP's setup installed, SYSTEM is a SQL administrator through `BUILTIN\Administrators`; this is the method Workpc's Owner recovery was completed with by hand on 2 October 2026. Settings → Users then works unelevated right after install. How it behaves:

- Before registering anything it checks, read-only, that SYSTEM or `BUILTIN\Administrators` is an enabled member of `sysadmin`; if not, it logs a NOTE and changes nothing.
- It writes a fixed T-SQL batch and a command file into a new folder under `%ProgramData%\EtpReporting` that only SYSTEM and Administrators can change, registers a task named `ETP Reporting Owner Grant <random>` (no trigger, runs as SYSTEM), starts it, waits up to two minutes, reads the result, and **always** unregisters the task and deletes the folder, whatever happened.
- The batch takes no input. As SYSTEM it checks again that it is `sysadmin`, then grants `ALTER ANY LOGIN WITH GRANT OPTION` to every login of an **active Owner** row in `dbo.application_users` that lacks it, each name through `QUOTENAME`. It grants only to Windows **user** logins: never to a group (an Owner row naming `BUILTIN\Users` must not hand the right to every user of the PC) and never to SYSTEM, LOCAL SERVICE, NETWORK SERVICE or an `NT SERVICE\` account. A login that already holds the right is skipped, so running setup again changes nothing.
- It never stops setup or the restore. The outcome is one line in the log, and a read-only check follows. Only if the Owner running setup still lacks the right does the log say `NOTE: ... still does not hold ALTER ANY LOGIN WITH GRANT OPTION` (restore helper: `NOTE: ... does not hold ...`), with the exact command below filled in for that Owner and instance; until then Settings → Users keeps asking that Owner for **Run as administrator**, and everything else works unelevated.
- The grantor of that right is then SYSTEM's SQL administrator session, not an Owner. If another Owner later demotes or deactivates that Owner from an unelevated ETP and SQL Server keeps the right because of that, the procedure refuses with 51473 (nothing changed); save again from an ETP started with **Run as administrator**. (Not yet observed on a real instance.)

**Fallback, by hand.** When the log has that NOTE, run the command it gives once, from an elevated Windows PowerShell, or this one with the Owner's identity and the instance in place of the examples:

```powershell
$sqlcmd = 'C:\Program Files\Microsoft SQL Server\Client SDK\ODBC\170\Tools\Binn\SQLCMD.EXE'
$action = New-ScheduledTaskAction -Execute $sqlcmd -Argument '-S .\SQLEXPRESS -E -b -d master -Q "GRANT ALTER ANY LOGIN TO [WORKPC\Sagar] WITH GRANT OPTION"'
Register-ScheduledTask -TaskName 'EtpOneOffOwnerGrant' -Action $action -User 'NT AUTHORITY\SYSTEM' -RunLevel Highest -Force | Out-Null
Start-ScheduledTask -TaskName 'EtpOneOffOwnerGrant'; Start-Sleep -Seconds 15
(Get-ScheduledTaskInfo -TaskName 'EtpOneOffOwnerGrant').LastTaskResult   # 0 means granted
Unregister-ScheduledTask -TaskName 'EtpOneOffOwnerGrant' -Confirm:$false
```

Then open ETP normally as that Owner: Settings → Users no longer asks for administrator rights. If the result is not 0, SYSTEM is not a SQL administrator on this instance; have one connect and run the same `GRANT` in `master`. Never grant the right to the shared staff account or the automation account. If setup's log says its one-off task or folder could not be removed, delete the `ETP Reporting Owner Grant …` task in Task Scheduler, or the `OwnerGrant-…` folder under `%ProgramData%\EtpReporting`, by hand.

**Deactivating without elevation.** Settings → Users turns **Save user access** off for an unelevated Owner without the grant option only when the change leaves the account active (adding, reactivating, promoting or changing a role). Deactivating an account (untick **Active**) stays possible: for an account with no SQL Server login, such as the old PC's accounts after a restore, nothing changes at server level, so it succeeds unelevated. Deactivating an account that does have a login still revokes `ALTER ANY LOGIN` from it; without the grant option SQL Server refuses that, nothing is changed, and the screen asks for **Run as administrator**.

**The last Owner.** The procedure refuses (51230) demoting or deactivating an Owner when no other active Owner could still sign in on this PC, that is, has a SQL Server login or a Windows account that still resolves. The old PC's Owner rows that a restore brings along do not count (security review 1.9.3, F4).

SQL `sysadmin` retains the documented emergency path in the role guards and can change database security objects. This is a trusted administrative capability, not a staff account permission. Protect and review its use. Module-signing keys and backup-recovery keys serve different purposes and must remain separately controlled.

Run signed `invoke-database-maintenance.ps1` as Owner/SQL administrator with the explicit approved local instance and database. It performs integrity checks, updates statistics and copies old audit rows to the archive; originals remain append-only. Its default archive age is 730 days. It does not shrink the database or delete audit history.

## When Tally and ETP disagree

This applies once Tally batches are in use (Phase 7). ETP never deletes, changes or re-dates a voucher in Tally, and never sends a whole batch again.

1. **Stop writing.** Do not write or import the same Tally file again, even if a voucher seems to be missing.
2. **Find out what Tally holds.** In Tally, open the company named on the batch, export the Day Book for the batch's dates (all vouchers, not a filtered view), and load the file into ETP. Compare again. A read-back that does not name its company, or names another one, proves nothing.
3. **Isolate.** Look only at the vouchers ETP lists as differences. Each row says what differs and what to do.
4. **Get the plan approved.** ETP proposes one step per voucher: read back again, correct the voucher in Tally by hand with the accountant, reverse it with a Credit Note and issue a fresh one (needs separate approval), or accept a warning with a reason. The Owner approves the plan before anything is done.
5. **Apply.** The accountant makes the approved corrections in Tally. ETP only prepares reversals as new batches.
6. **Check again.** Export the Day Book again, load it, and compare. Earlier comparisons stay on record unchanged.
