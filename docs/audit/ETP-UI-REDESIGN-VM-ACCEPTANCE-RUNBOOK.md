# ETP redesign — remaining acceptance run

Prepared 12 September 2026. Target: **1.8.8-r9**, identified by its source and artifact receipt, not HEAD alone. This is a prepared procedure; its steps are **NOT RUN** until recorded against the installed application. No production deployment is authorised.

## Start and protect the baseline

1. Read the current [ledger](../design/ETP-UI-REDESIGN-SPRINT-LEDGER.md), [acceptance record](ETP-UI-REDESIGN-ACCEPTANCE.md) and candidate receipt. Check the already requested VM worker is actually connected; a VM connection window alone is insufficient. Do not request or record credentials in evidence.
2. Execute the existing read-only baseline job on `ETP-Acceptance-186`. Record installed executable path, SHA256, version, Windows/SQL versions, account role, database identity, client bounds and scaling. Historical original fixture expectations are 3 sales rows, 2300 net, signed quantity 2, 1 imported source and 3 lineage rows. Treat a mismatch as a finding; do not alter data to obtain the expected result.
3. Preserve a verified original database backup and its checksum/restore-verification evidence. Capture current settings/preferences and installation identity in the protected local evidence location. Do not put private settings in the portable evidence bundle.
4. Compare the installer/executable against the r9 receipt. Install only on the acceptance VM, retaining the existing working installer. Verify the **installed** executable hash after setup and observe a launch. Neither installer exit code nor a running process establishes UI acceptance.
5. Use a separately named disposable database and the existing synthetic 25 August 2026 workbooks. Establish its counts before each mutating journey. Never run restore, restatement, cancellation experiments or fixture seeding against the protected original database.

## Record each observation

Use the [527-row route coverage](../design/ETP-UI-REDESIGN-ROUTE-COVERAGE.csv) for exact canonical routes and actions. A search result must show that same full path. For each case record: timestamp, candidate SHA256, Windows identity/role, database/fixture, starting route, input, expected result, observed result, screenshot or video, physical resolution, scale, actual client DIPs, density, input method, resulting data counts and PASS/FAIL/UNVERIFIED.

Run positive, negative, missing/empty and busy cases where applicable. Record NOT APPLICABLE with a concrete reason rather than manufacturing a state. Keep failed attempts and link their passing reruns. Service results and actual UI observations occupy separate fields. Screenshots must exclude unrelated applications and private data.

## Required matrices

- Physical desktop resolutions: 1366×768 and 1920×1080, each at 100%, 125%, 150%. Record actual client DIPs; do not relabel a 96-DPI offscreen image as a native scaling test.
- Client layouts: 1280×720, 1000×600, 960×600, 800×440, 1024×768, 1280×800, 800×1000 and return to landscape. Test Comfortable and Compact. Every distinct task/dialog needs normal-size review; shared patterns and custom layouts need the full matrix.
- Variations: long labels/path/errors, large numbers, signed returns, many rows, missing values and explicit zero. For large tables, verify scroll/selection responsiveness and virtualization in the running app.
- Performance: at least 30 warm loaded-shell transitions, p95 ≤500 ms; search p95 ≤250 ms and first opening ≤1 s. Record machine, warm/cold state and stopwatch methodology. Compare startup/memory/navigation to the starting build under the same conditions; investigate unexplained regressions above 20%.

## Recovery and closure

If setup or migration fails, preserve logs and the verified backup. Do not launch the failed installation as though setup succeeded, delete the original database, or attempt automatic reverse migration. Restore only a separately verified compatible backup into an isolated recovery target; validate counts, lineage and application health before changing any test connection.

When each installed case has evidence, update its UX/J and route columns. Recheck original protected counts and restore temporary settings; remove only the exact generated disposable databases after validating their names. Any source repair requires new tests, an immutable new candidate and new hashes. The sprint becomes COMPLETE only when every mandatory criterion passes; production deployment remains outside this run.
