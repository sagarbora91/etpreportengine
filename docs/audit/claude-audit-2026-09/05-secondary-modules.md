# 05 — Secondary modules: functional-completeness audit

Date: 2026-09-15. Scope: Accounting, Archive/Sharing, Operations Center / Exceptions / Approvals, Settings & Administration, Help Centre, navigation catalogue, startup/lifecycle. Dashboard, Daily Workflow, Reports and Imports are audited separately and are only referenced where a secondary module routes into them.

Method: every button/command handler in the module views was traced UI → presentation session → `Etp.Reporting.Application` contract → `Etp.Reporting.Infrastructure.SqlServer` adapter → T-SQL → migration that defines the table. Read-only; the app was not run. Paths below are relative to `src/` unless stated. Line numbers are from the current source.

Status legend: **Working** = full UI→SQL→UI path exists and the SQL matches the schema. **Partial** = path exists but a material piece of the advertised feature is missing or inert. **Stub** = screen/handler exists but performs no real operation or is an alias of another screen. **Missing** = advertised (nav item, help text, doc) but no implementation.

### 6.2 `ResolveTaskView` index arrays — fragility assessment

`TaskNavigator.ResolveTaskView:422-481` selects which children of each workspace's root `StackPanel` to show by **positional index** (`body`/`actions` int arrays), and `FocusedTaskLayout.Show:17-91` physically detaches every child, rebuilds a Grid from `parts.Children[index]`, and moves buttons out of the `actions` panels into a toolbar. I checked every array against the current XAML child order (Accounting 10 children, Archive 11, Operations 30, Investigation 10, Administration 15, Settings 6): all indices are in range today.

Fragility:
1. Any insertion/removal/reorder of a XAML child silently shifts every later index. No test asserts child counts or index validity (the view tests read XAML as text but not structure). An out-of-range index throws `IndexOutOfRangeException` at `FocusedTaskLayout.cs:45/73/85` **after** the children have already been removed from their parents (line 33-36) → the dispatcher handler shows the generic MessageBox and the workspace is left with a detached child list; every later navigation to that view is broken until restart.
2. `FocusedTaskLayout.cs:74-84` hard-codes `title == "Watch Folder" && index == 12` and iterates `12..19` — a second positional coupling to `OperationsWorkspaceView.xaml` from a different file.
3. `SettingsWorkspaceView.SelectIntegrationTask:71-79` uses a third positional scheme (`index < 2 || index == 10 || 6..9 / 2..5`) over `ProductSettingsPanel`.
4. Primary-button selection is by caption prefix (`FocusedTaskLayout.cs:52`: "Save"/"Submit"/"Update"/"Verify extraction") and Reject/Waive exclusion by caption (line 55) — renaming a button changes styling.
5. Buttons are moved between parents on every navigation (lines 29-32, 47) — visual-tree churn that `SelectionReasonDrafts`/`CaptureIssueActions` (`OperationsTaskState.cs:13`, captured once in the ctor) tolerate only because they hold references, not paths.

Recommendation: replace index arrays with `x:Name`-based lookups (`view.FindName`) or per-task named `Grid` regions; add a test that instantiates each view and asserts `Children.Count` equals the maximum index + 1 used for it.

## 10. Summary

What is genuinely end-to-end in the secondary modules:
- Accounting prepare → save → Owner approve → Tally XML export (with a real, atomic, hashed XML writer).
- Archive search → SHA-verified open → compare → Excel/PDF re-export → ZIP package with manifest.
- Operations trend analytics, data-quality issue workflow, adjustment request → Owner decision, global investigation search.
- Watch-folder import + scheduled packs when run on demand or from the installed Windows task.
- Users & roles with real SQL principal provisioning; connection/bootstrap/migrations with a proper app lock.

What the docs/nav claim but the code does not deliver:
- Mapping Review, Validation, Export History, Accounting Reconciliation — aliases.
- Shared Reports history, WhatsApp attachment, SMTP email sending — absent (`share_attempts` write-only; SMTP never used).
- Stores / Master Data / Tender Rules — write-only tables with no consumer; stores are hard-coded.
- Approval Centre for restatements, reopen-day, master mapping, control waivers — no producers.
- System Health under Settings — a subset; the real health lives on the Dashboard.
- Background watch-folder polling — none in-process.
- Backup / recovery drill / support package — packaged builds only, and the drill needs server-level SQL rights.

Two defects will surface in the first week of real use: **C-1** (an approved adjustment blocks Accounting for that day) and **C-2** (the first failed import or restatement makes the Operations Center refresh throw a CHECK-constraint violation for every Store Manager and Owner). Both live in untested T-SQL.

Priority fixes: C-1, C-2, H-1 (last-Owner guard), H-2 (CLI modes honour settings.json), M-1 (persist approval reason), M-7 (ship scripts with the build or fail gracefully), then replace the index-based task layouts (H-3).
