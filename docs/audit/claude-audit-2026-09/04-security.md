# 04 - Security review (defensive, read-only)

Date: 2026-09-15. Scope: ETP Reporting Engine 1.8.8 (.NET 10 WPF + SQL Server Express). Repository root `C:\Codex\Reporting Manger\SaagarCC-V6-ETP-Source-and-Report-Engine-605002f`. All paths below are relative to that root. `www/`, `graphify-out/`, `artifacts/`, `node_modules/`, `bin/`, `obj/` were ignored. No source, test or doc file was modified; nothing was executed against a database or the installer.

Threat model used: one PC or a small LAN; Windows-integrated SQL auth only; roles Owner / Store Manager (SM) / Viewer in `dbo.application_users` keyed by `SUSER_SNAME()`; unattended automation runs as `NT AUTHORITY\SYSTEM`; backups, exports and source documents on local disk; PowerShell scripts launched from the app and from scheduled tasks; data is financial and source workbooks carry customer names/phones.

Severity scale: Critical = immediate loss of confidentiality/integrity by an ordinary local user; High = privilege escalation or integrity bypass reachable by an assigned role; Medium = weakens a stated control or needs a second condition; Low = hygiene.

Overall verdict: the codebase is unusually careful for its size (parameterised SQL everywhere, allow-listed audit vocab, reparse-point checks, checksum-verified backups, fail-closed migrations, Windows-only auth enforced twice). The material weaknesses are (a) a Store Manager's SQL grants are broader than the business rules the app enforces, so several Owner-only workflows are UI/adapter-only; (b) automation runs as SYSTEM and executes an Owner-configurable binary; (c) database backups and source documents sit in `%ProgramData%` with default (all-users-readable) ACLs and no encryption; (d) nothing is code-signed.

### Automation identity (`NT AUTHORITY\SYSTEM`)

- Provisioned as a STORE_MANAGER with `db_backupoperator` (`0012:10-20`) and hardened with DENYs (`0013`, `0014:508-524`).
- **Unverified assumption (High if true):** SQL Server setup normally creates the `NT AUTHORITY\SYSTEM` login and, on most 2019/2022 installs, it is a member of `sysadmin`. Migration `0012:4-5` only creates the login if it is missing and never checks or removes `sysadmin`. A `sysadmin` member ignores every `DENY`, so all of `0013`/`0014` would be decorative and the automation task would run with full instance rights. Verify on the deployed instance with `SELECT IS_SRVROLEMEMBER('sysadmin', N'NT AUTHORITY\SYSTEM')`. If it returns 1, either drop that membership (supported by Microsoft since 2012) or, better, run the task as a dedicated least-privilege account (see 1.9).
- 1.8 **Owner-controlled binary executed as SYSTEM (High).** `product_settings.ocr_helper_path` is a free-text path saved by any Owner (`ProductisationRepository.cs:49-68`, only `Clean()`; no allow-list, no hash, no directory confinement). The unattended task (`scripts/install-etp-automation-task.ps1:10-14`, `-User SYSTEM -RunLevel Highest`) picks up PDFs/images from the inbound folder (`AutomatedOperationsService.cs:44-49`) and runs `PaddleOcrProcessExtractor` on them (`ProductisationOperationsService.cs:41-46` -> `DocumentIntakeService.cs:41-63`, `Process.Start(helper)`). Result: an Owner who is *not* a Windows administrator (or anyone who becomes `db_owner`) gets arbitrary code execution as SYSTEM by pointing the OCR helper at a script/exe and dropping one image in the watch folder. `SafeExistingFile` (`DocumentIntakeService.cs:83-89`) only rejects reparse points.
- 1.9 Same task parses attacker-supplied XLSX/ZIP/PDF as SYSTEM from a folder whose ACL the app never checks (`AutomationPathPolicy.Canonical`, `Phase2OperationsRepository.cs:496-505`, rejects roots/UNC/reparse only). Anyone with write access to the inbound folder injects "trusted" imports attributed to `NT AUTHORITY\SYSTEM`. Medium. SYSTEM also creates/moves files into Owner-chosen local folders (`AutomatedOperationsService.cs:26-30`, `181-186`) - path validated once, no re-check before `File.Move` (TOCTOU with junctions). Low.
- The monthly recovery-drill task is registered **without** `-User`/`-Principal` (`scripts/install-monthly-recovery-drill-task.ps1:15`), so it runs as the installing admin, only while that user is logged on. Inconsistent with the other two tasks and likely to never run on a store PC. Medium (see section 6).

### The "elevated admin token" requirement for reopening (`DailyWorkflowWorkspaceView.xaml.cs:412-416`)

`IsCurrentWindowsAdministrator()` returns true only for a UAC-elevated token. Consequences:

1. It is client-side theatre: the boolean travels to `DailyReportingWorkflowRepository.ReopenAsync` as a parameter (`:145-148`) and SQL never rechecks; a 10-line console program, or the direct `UPDATE` in 1.1, ignores it.
2. It conflates OS privilege with business authority. An Owner who is not a local admin can never reopen a day (operational lock-out), which in practice pushes the business to make the Owner a local administrator - the one thing that makes them a de-facto SQL `sysadmin` on Express (setup adds the installing admin to `sysadmin`) and defeats the whole DENY model.
3. To satisfy it the Owner must launch the entire WPF app "Run as administrator". Everything the app then spawns is elevated: `Process.Start(...UseShellExecute=true)` on report files (`Modules/SourceInbox/SourceDocumentLauncher.cs:20`, `Modules/Archive/ArchiveShareLauncher.cs:297`), `explorer.exe`, `powershell.exe -ExecutionPolicy Bypass` for backups/drills (`PowerShellOperationsService.cs:28-41`). An elevated app opening untrusted xlsx/pdf is a worse posture than the check was meant to buy.
4. It gives no protection against 1.1.

Assessment: **remove it** (Medium). Replace with a SQL-enforced rule: a trigger (or a stored procedure that is the only granted path) on `daily_reporting_days` that allows `LOCKED -> OPEN` only when `IS_ROLEMEMBER('db_owner')=1` (or a dedicated `etp_owner` role) *and* a non-empty reason is written to `daily_reporting_events` in the same statement. If a second pair of eyes is wanted, route reopen through `approval_requests` (already Owner-decided at SQL, `ProductisationRepository.cs:260-261`) instead of a Windows token.

### Other authorisation notes

- 1.10 Owner receives server-level `ALTER ANY LOGIN` (`Phase2OperationsRepository.cs:136`). Necessary for `CREATE LOGIN ... FROM WINDOWS`, but it also permits disabling or re-passwording *any* login on the instance (including SQL logins of other databases if the instance is ever shared). Low; document as accepted or move provisioning to a signed stored procedure executed as a fixed principal.
- 1.11 The identity regex (`Phase2OperationsRepository.cs:64`) accepts group names such as `BUILTIN\Users`. `CREATE LOGIN [BUILTIN\Users] FROM WINDOWS` would give every local user datareader/datawriter/db_owner via the group while `SUSER_SNAME()` (the individual) never matches `application_users`, so the app says "no access" but SQL says yes. Low; reject group SIDs (`SUSER_SID` type `G`) or require `DOMAIN\user` to resolve to a user principal.
- 1.12 First-Owner seeding: whoever runs the first bootstrap becomes Owner (`0011:26-28`), and an unassigned user may click "Create/Update database" (`SettingsWorkspaceView.xaml.cs:239-243` allows it when no role is assigned). Fine for install; note that a non-owner with `db_owner` rights (the installing admin) can always rewrite `application_users` - accepted by the threat model, but there is no documented break-glass procedure for "the only Owner's Windows account was renamed/deleted". Low.
- 1.13 `remove-etp-scheduled-tasks.ps1` and the uninstaller keep databases and backups (good, documented).

## 2. SQL injection

- All application SQL is parameterised (`SqlCommand` + `AddWithValue`); list filters go through `OPENJSON(@stores)` etc. with JSON built by the caller (`OperationalReportRepository.cs:171-173,230-233`, `SqlServerReportingQueryRepository.cs:23-26`). No string-built predicates were found. OK.
- Dynamic SQL exists only in login provisioning (`Phase2OperationsRepository.cs:66-137`): every identifier passes through `QUOTENAME()`, values are parameters, and the identity is pre-validated by regex (`:64`). OK.
- `CREATE DATABASE [{databaseName}]` (`DatabaseBootstrapper.cs:23`) is interpolated but guarded by `^[A-Za-z0-9_-]{1,128}$` (`:33`); `]` cannot appear. OK.
- PowerShell -> `sqlcmd -Q`: `$Database` is regex-checked in every script (`backup-etp-database.ps1:20`, `invoke-etp-recovery-drill.ps1:11`, `new-etp-support-package.ps1:11`, `invoke-database-maintenance.ps1:5`); file paths and logical names are `'`-doubled. Two hygiene points: (a) `sqlcmd` performs `$(name)` variable substitution inside `-Q` text unless `-x` is passed - a username or path containing `$(` (unlikely but possible) breaks or substitutes; add `-x`. (b) In the recovery drill the logical file names come from `RESTORE FILELISTONLY` of a backup file chosen by "newest `*.bak` in a directory any local user can write to" (see 4.3). Low.
- Connection string from user text (`Modules/Settings/ConnectionStringValidation.cs:15-40`, plus the second gate `SqlAdapterConnection.RequireWindowsIntegrated`, `SqlAdapterConnection.cs:22-27`): `User ID`/`Password`/synonyms are rejected both by regex on the raw text and by the parsed builder, so credentials cannot be persisted or used. Good. Not restricted: `Data Source` (any host, `tcp:`), `Encrypt=False`, `TrustServerCertificate=True` (also the shipped default, `Composition/DesktopCompositionRoot.cs:44-45`), `AttachDbFilename`, `Authentication=...`. A user can therefore point *their own* session at a remote host, sending their NTLM credentials there (relay/capture on a LAN), or downgrade transport security. Because settings are per-user in `%LOCALAPPDATA%` this only affects that user. Low on a single PC, Medium if the LAN is untrusted. Recommend allow-listing `Data Source` to local forms (`.\SQLEXPRESS`, `(local)`, `localhost`, `lpc:`/`np:` prefixes) and rejecting `Encrypt=False`/`AttachDbFilename`.

No SQL-injection finding above Low.

## 3. Command / script injection

- `PowerShellOperationsService.cs:15-49`: script name allow-list (`:12-13`), path confined to `{app}\scripts` and checked for reparse points (`:18-22`), `ProcessStartInfo.ArgumentList` (no shell quoting bugs), `-NoProfile`. Only `-ServerInstance <DataSource>` and `-Database <catalog>` are passed (`:51-60`); the catalog is regex-checked, the data source is whatever the connection string held. Values bind to `[string]` script parameters, so no code injection. OK.
- `-ExecutionPolicy Bypass` is required because nothing is signed (see 7). Acceptable only while the scripts live under an admin-only directory; it becomes a real weakness under 7.3.
- `FileName = "powershell.exe"` (`:28`) relies on search order (application directory first). Under Program Files that is fine; a per-user or portable install would let a planted `powershell.exe` in the app folder win. Use the absolute `%SystemRoot%\System32\WindowsPowerShell\v1.0\powershell.exe`. Low.
- Only the last stdout/stderr line (300 chars) is shown to the user (`:62-63`); the backup script's last line is the `Get-FileHash` `Path :` row, i.e. the backup path is displayed in the UI toast. Not persisted to audit. Low.
- Scheduled tasks (`install-daily-backup-task.ps1:9-13`, `install-etp-automation-task.ps1:10-14`): SYSTEM, `RunLevel Highest`, `-Force`, absolute paths from `$PSScriptRoot`. Fine as long as `{app}` is admin-only (see 7.3). The drill task has no principal (`install-monthly-recovery-drill-task.ps1:15`) - see 1 and 6.
- Scripts' own parameter handling: all use `-LiteralPath`, `[IO.Path]::GetFullPath`, `ValidateRange`, GUID-suffixed temp files, and refuse to overwrite existing backups/receipts (`backup-etp-database.ps1:34,55`). `bootstrap-etp-prerequisites.ps1` requires an elevated caller (`:108-112`) and verifies the pre-migration backup receipt by hash and directory prefix (`:85-106`). Good.
- The OCR helper (`DocumentIntakeService.cs:53-63`) is the one place an operator-configurable executable is launched; see 1.8.
- `SafeShareLauncher.CreateWhatsAppUri` (`AccountingAndSharingServices.cs:77-84`) URL-encodes the message and digit-filters the phone before `Process.Start(uri)`; `.eml` headers reject CR/LF (`:100-104`). OK.

## 4. File system

- 4.1 **Backups world-readable and unencrypted (High).** `backup-etp-database.ps1:36` writes `BACKUP DATABASE ... WITH COPY_ONLY, CHECKSUM, INIT` - no `ENCRYPTION`, no media password - into `%ProgramData%\EtpReporting\Backups`. The bootstrap creates that folder with `New-Item -Force` (inherits ProgramData defaults: BUILTIN\Users can read files and create files/folders) and only *adds* Modify for the SQL service (`bootstrap-etp-prerequisites.ps1:153-155`). Any local account - a Viewer, a kiosk user, or someone with no application role at all - can copy every `.bak` (full customer/financial data) with Explorer, and can also drop files there (4.3). Retention is "indefinite by policy" (`install-daily-backup-task.ps1:13`) with only free-space warnings (`backup-etp-database.ps1:29-30`), so the drive eventually fills. Fix: `icacls` the folder to `SYSTEM`, `Administrators`, `NT SERVICE\MSSQL$SQLEXPRESS` (remove inherited Users), enable BitLocker or `BACKUP ... WITH ENCRYPTION` under a documented certificate-custody process, and add a rotation (keep N daily + M monthly).
- 4.2 Same ACL issue for `product_settings` defaults `C:\ProgramData\EtpReporting\Documents` and `...\Share` (`0014:24-25`): scanned invoices/registers (`ManagedDocumentRepository.StoreAsync`, `DocumentIntakeService.cs:108-134`) and `.eml` drafts with base64 report attachments (`AccountingAndSharingServices.cs:86-98`) are readable by all local users. Medium.
- 4.3 Recovery drill trusts the newest `<db>-*.bak` in that writable directory (`invoke-etp-recovery-drill.ps1:13-14`) and restores it on the production instance (isolated DB name, `MOVE` into `Backups\RecoveryDrill`, dropped in `finally` - good). A planted backup can at least fill the disk or fail the drill; it cannot overwrite production (no `REPLACE`, unique name). Low/Medium; fixing 4.1 closes it. Better: restore the file named in the last verified receipt and check its SHA-256 (the receipt machinery already exists, `backup-etp-database.ps1:43-52`).
- 4.4 ZIP extraction (`Import/Batch/ImportPathPolicy.cs`, `BatchImportSource.cs:91-115`): rooted/`..` entries rejected by canonical-prefix check (`ImportPathPolicy.cs:92-101`), symlink entries rejected (`:119-123`), depth/entry-count limits, `FileMode.CreateNew`, only `.xlsx` entries, temp dir per run (`BatchImportSource.cs:37`). Zip-slip is handled. Gap: ratio and size limits use the attacker-controlled central-directory `Length` (`ImportPathPolicy.cs:80-88`); the actual inflate (`BatchImportSource.cs:109`) is unbounded, so a bomb with forged sizes fills `%TEMP%` (for the SYSTEM task that is `C:\Windows\Temp` on the system drive). Wrap the output stream in a byte-counting stream that aborts past `MaximumEntryBytes`. Low/Medium.
- 4.5 Exports go only where the user's `SaveFileDialog` points (`ReportsWorkspaceView.xaml.cs:143,156`, `ArchiveWorkspaceView.xaml.cs:135-172`); the Excel filename uses `ReportName.Replace(' ', '_')` while PDF uses `SafeFileName` (`:378`) - harmless today because names are catalogue constants, but inconsistent. Automation output names are sanitised (`AutomatedOperationsService.cs:148-151`). Low.
- 4.6 `settings.json` (`%LOCALAPPDATA%\EtpReporting`): holds server+database only, never credentials (enforced on save and load, `DesktopSettingsStore.cs:24-89`), atomic temp+move, reparse-point walk of every segment (`:91-114`). Good.
- 4.7 `SourceDocumentLauncher.Open` (`Modules/SourceInbox/SourceDocumentLauncher.cs:17-32`) shell-opens `source_documents.managed_path` from the DB. A Store Manager can UPDATE that column (1.5) to a UNC path or any local file with an allowed extension; the Owner then opens it (NTLM leak / phishing document). Add "must be under the configured document repository" and a reparse check. Low.
- 4.8 Temp files: import staging, OCR JSON (`DocumentIntakeService.cs:50`) and package staging (`Reporting/ReportPackageService.cs:29`) all use GUID names under `%TEMP%` and are deleted in `finally`. OK.
- 4.9 Reparse-point checks are check-then-use throughout (settings, automation folders, scripts). Acceptable for this threat model; noted so nobody reads them as a hard guarantee.

## 5. Privacy

- Diagnostics (`DesktopDiagnostics.cs:19-27, 60-68`): each `.jsonl` line carries timestamp, severity, event id, source, correlation id, exception *type*, HResult and version - never the message, stack, path or SQL text; tokens are whitelisted to `[A-Za-z0-9.:_-]` (`:142-149`); 180-day / 24-file / 5 MB retention (`:31-33`). This is well above the norm. Nothing to fix.
- `operational_audit.safe_detail`: app-side rule forbids `\`, `/`, `:` and any digit (`OperationalAuditRepository.cs:27,55`); triggers and scripts insert fixed literals. But the rule is not a SQL `CHECK`, and INSERT is granted to everyone (1.6), so the guarantee holds only for rows the app wrote. Medium (shared with 1.6).
- `automation_runs.source_file_name` stores the inbound file name up to 260 chars (`Phase2OperationsRepository.cs:287-296`); watch-folder file names may embed store/customer identifiers and are visible to Viewers. Low.
- Free-text `change_reason` / `reopen_reason` / `remarks` columns are Viewer-readable and unvalidated for PII. Low; state it in the user guidance.
- Support package (`scripts/new-etp-support-package.ps1`): aggregate counts, OS caption/version/boot time, service and task states, a `privacy.txt` statement. `2>&1` on the health query (`:29`) can capture a sqlcmd error that names the instance or the login (`Login failed for user 'DOMAIN\x'`). Low. No connection strings, no rows, no source names. Good.
- Usernames: audit rows, `application_users`, `*_history`, `modified_by` columns all store Windows identities by design; `sharing_contacts` stores email/phone of recipients (Viewer-readable, see 1). Low/Medium.
- Connection strings are never logged; health messages are generic (`ConnectionHealth.cs:30-41`). The UI's `DesktopFriendlyError.Describe` shows exception text on screen only. OK.

## 6. Data integrity

- Imports are transactional per workbook (`SqlServerRepositories.cs:42-50, 93-110`; `RetailEnrichmentSqlImportOrchestrator.cs:64-128`), de-duplicated by SHA-256, and restatements go through `prepare_import_restatement` which archives prior facts into an immutable table (`0010:242-253, 262-323`). Good.
- Locked-day protection is enforced by triggers on every fact and manual-input table (`0005`, `0009`, `0010`), but the lock *state itself* is unprotected (1.1). That is the single integrity gap that matters.
- Report generations are immutable except the one-way `is_final` flag (`0011:190-206`) and re-export verifies the stored SHA-256 (`Phase2OperationsRepository.cs:365-376`). Good.
- Audit immutability: UPDATE/DELETE denied to SM and SYSTEM only; the Owner (`db_owner`) can rewrite or delete `operational_audit`, there is no trigger, no hash chain, and `invoke-database-maintenance.ps1:7` deletes by age. Medium. If the audit is meant to bind the Owner too, make it append-only via an `INSTEAD OF UPDATE, DELETE` trigger plus a scheduled export to write-once storage, or a SQL ledger table.
- Backup verification: `RESTORE VERIFYONLY WITH CHECKSUM` (`backup-etp-database.ps1:36`), SHA-256 receipt (`:43-52`), receipt validated before migration (`bootstrap:85-106,175-176`), dashboard tracks last successful backup age and free space (`DatabaseOperationalHealth.cs:13-23`). Good. Note RPO: one COPY_ONLY full per day on a SIMPLE-recovery database means up to 24 h of imports/manual inputs are lost on media failure. Medium (business decision; a second daily run or log backups would need FULL recovery).
- Restore drill: isolated name, `MOVE` to a drill folder, `DBCC CHECKDB`, drop in `finally` (`invoke-etp-recovery-drill.ps1:17-60`) - the target-database safety is right. Weaknesses: (a) the task probably never runs (no principal, 1/3); (b) it compares only `import_files`/`source_lineage` counts against *live*, so any import since the backup produces a false failure and no fact table is checked; (c) from the app the drill needs `CREATE DATABASE`, which a least-privilege Owner (db_owner only) does not have - the "Run recovery drill" button will fail unless the Owner is sysadmin. Medium.
- Migrations: fail-closed on checksum mismatch or missing applied id (`Migrations.cs:55-61`), exclusive `sp_getapplock` (`:109-118`), one transaction per script (`:174-191`), scripts themselves `SET XACT_ABORT ON`. Good. Two operational risks: the checksum is over raw bytes, so a CRLF/LF normalisation (git `autocrlf`, an editor) of an already-applied script bricks startup until someone edits `schema_migrations` by hand (Low - normalise line endings before hashing); and migration files ship as loose `.sql` under `{app}` (`Etp.Reporting.Desktop.csproj:25`), editable by any admin with no binding to the binary (accepted).

## 7. Process / supply chain

- Build hygiene: `TreatWarningsAsErrors`, `Nullable`, `Deterministic`, `ContinuousIntegrationBuild` (`Directory.Build.props`). CI (`.github/workflows/ci.yml`) restores, parses every `.ps1`, builds Release, runs the .NET suite, `npm ci --ignore-scripts`, then a **fail-closed** `dotnet list package --vulnerable/--deprecated` + `npm audit` (`scripts/invoke-security-scan.ps1:104-182`), with `permissions: contents: read`. Good.
- 7.1 **No Authenticode signing anywhere (Medium).** `scripts/build-windows-release.ps1:39-40` publishes without signing; `installer/EtpReportingEngine.iss` has no `SignTool`; the "signing credentials" gate in `build-production-release.ps1:76-84` is the Android keystore for the `www/` app, not Windows. The licensing spec already notes this (`docs/security/ETP_LICENSING_ENGINEERING_SPEC.md:618`). Effect: SmartScreen warnings, no tamper evidence for an installer that runs elevated PowerShell with `-ExecutionPolicy Bypass` (`.iss:50,60-63`), and scripts that must stay unsigned.
- 7.2 Self-contained single-file publish (`build-windows-release.ps1:39-40`): the .NET 10 runtime is frozen into the exe, so runtime CVEs need an app re-release rather than Windows Update; `IncludeNativeLibrariesForSelfExtract` extracts natives to `%TEMP%\.net\...` at run time (user-writable; `C:\Windows\Temp` for the SYSTEM task). Medium/Low. Consider framework-dependent + a runtime prerequisite, or at least `IncludeNativeLibrariesForSelfExtract=false`.
- 7.3 `PrivilegesRequiredOverridesAllowed=commandline` (`.iss:26`) lets an operator install to a user-writable directory; the bootstrap then registers SYSTEM tasks pointing at `{app}\Etp.Reporting.Desktop.exe` and `{app}\scripts\*.ps1`. ## 8. Licensing design (`docs/security/*`, deferred)

Nothing licensing-related exists in `src/` (grep for licence/entitle/activation returns only ETP column names), and the backlog is explicitly on HOLD (`ETP_LICENSING_IMPLEMENTATION_BACKLOG.md:3`). So there is no half-implemented gate today. Risks to flag *before* Phase 6 ("startup enforcement") is ever executed:

- 8.1 The design fails closed to an ActivationWindow on `WrongDevice`, `CorruptActivation`, `InvalidSignature`, `Expired` (`ENGINEERING_SPEC.md:431-449`, backlog Phase 6) and states that SQL roles cannot bypass the gate (LIC-012). Combined with DPAPI `LocalMachine` binding (`:267`) and a hardware-change policy (`:281`), a motherboard swap, Windows reinstall, disk-image restore or DPAPI master-key loss locks the store out until the Owner, on a different PC, with the private key, with Microsoft login, issues a replacement licence (`:351-353`). The spec lists the private key as a single point of failure with an offline escrow (`:357-365`). Medium (future): require a documented grace/read-only mode (reports + backups keep working, imports blocked), an owner-signed emergency override with an expiry, and a rehearsed escrow restore before any enforcement ships.
- 8.2 `--automation-once` is to be gated centrally (backlog Phase 6). Backups are PowerShell and unaffected, but unattended imports would stop silently on a licence fault. Ensure the automation run records an `AutomationRun/Blocked` audit row so the dashboard shows it.
- 8.3 `Expired` exists as a status while the payload example has `expiresAtUtc: null` (`:217`). Make the clock-independence explicit (no expiry for perpetual licences; if dated, compare against last-seen-time to resist clock rollback without locking out on a wrong BIOS clock).
- 8.4 Unrelated to licensing but the same lock-out class: the only Owner losing their Windows identity (rename, domain move, profile corruption) has no in-product recovery; recovery is "sysadmin edits `application_users` in SSMS". Write that break-glass procedure down now (Low).
