# Function-first synthetic acceptance audit

This audit is the executable answer to “are we covering every function?” It derives scope from the active WPF/.NET runtime registries and public application contracts instead of maintaining a separate hand-written feature list.

Run from the repository root:

```powershell
./scripts/Invoke-EtpFunctionAudit.ps1
```

The runner creates 12 deterministic-data workbooks: the six approved import profiles for each of the two stores. It validates them offline, builds and tests the complete solution, renders every executable workspace and all 29 report routes, verifies Excel/PDF/DSR export, exercises the performance budgets, and executes the live SQL workflow against a uniquely named disposable SQL Server Express database. Live coverage includes bootstrap and migrations, imports and duplicate detection, reports and controls, daily workflow, manual zero values, report packs, permissions and administration, archive and comparisons, automation, backup verification, restore, and lineage comparison.

Evidence is written beneath `verification/function-audit/current`:

- `function-coverage.json` and `.md` contain the runtime-derived traceability matrix.
- `expected-control-totals.json` defines the synthetic-data oracle.
- `fixture-evidence.json` records the matched profile, row count, and SHA-256 for every workbook.
- `audit-summary.json` and `.md` record each executed check and its result.
- `logs`, `exports`, `performance.json`, and `ui` contain supporting evidence.

The disposable database name is generated by the runner, validated against a narrow prefix and format, and dropped in `finally`. The script never accepts a database name and cannot target an existing product or production database.

## Meaning of complete coverage

Every active entry must have at least one assigned evidence layer. Critical paths have multiple layers. A matrix generation failure means the audit fails before SQL is touched. Explicitly unavailable UI entries remain in the matrix as `DEFERRED_UNAVAILABLE`, with their runtime reason; they are not silently counted as working features.

Some acceptance work cannot be honestly automated on a developer workstation and remains visible in every summary:

- signed installer installation and upgrade on a clean Windows workstation;
- observed keyboard-only, screen-reader, and display-scaling accessibility;
- installed email-client sharing and corporate-policy integration;
- production-like backup retention and restore operations;
- business-owner review of control totals and final user acceptance.

These are external gates, not coverage omissions. The audit is successful only for the automated environment it reports; it does not convert external acceptance into a synthetic pass.
